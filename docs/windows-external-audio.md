# Windows external-audio routing

## What is implemented

`sonicsync_wasapi.exe` now accepts an explicitly selected render endpoint as a WASAPI loopback source, processes captured frames through the shared `sonicsync::Processor`, and renders the result to a different selected physical endpoint. Live preset, Bass/Mid/Treble, bypass, route-state, peak-meter, and spectrum values are exchanged through the same-session named shared-memory control block. The route UI starts and stops this child engine, and it never changes Windows' default device. The status becomes active only after captured audio packets enter the processing path. Local WAV playback remains available as a separate route.

The concrete signal path is `app -> selected source render endpoint -> WASAPI loopback capture -> SonicSync DSP -> selected render endpoint`. The existing relay also checks that source and render endpoint IDs differ. If a physical speaker/headphone endpoint is used as the source, Windows continues rendering the original mix there while SonicSync sends another copy to the selected output; that can sound doubled or delayed. For the intended setup, the source must be an installed virtual playback endpoint and target apps must be explicitly routed to it. The relay does not verify that an endpoint is virtual based on its friendly name, and “processing” only means non-silent source samples reached the DSP. It is not proof that all apps are routed through it.

This is an explicit virtual-endpoint relay. It is not a transparent Windows effect: applications must send their audio to the selected virtual playback endpoint, and SonicSync must remain running to render that signal to the physical device. Applications left on a physical endpoint bypass SonicSync. WASAPI loopback followed by playback on a different endpoint is not called system-wide interception.

## Why this route, and alternatives

| Approach | Complexity and latency | Compatibility and installation | Decision |
|---|---|---|---|
| User-mode WASAPI loopback + separate virtual cable endpoint | Reuses this project's event-driven capture/render bridge and DSP; adds Windows shared-mode buffers and the cable's buffer. The bridge requests 20 ms shared buffers; end-to-end latency has not been measured and depends on endpoint/cable settings. | Uses a separate vendor-supplied Windows audio driver; user installs it and routes apps to its playback endpoint. Verify the acquired package signature and current vendor terms before installation. Shared-mode apps work when explicitly routed. Exclusive-mode apps on a physical device bypass this route. | Chosen as the lowest-risk feasible external-audio path. No default route changes and no driver is bundled or installed by SonicSync. |
| Endpoint APO | Runs in Windows' audio graph, so it can process streams routed through the associated endpoint without a user-mode capture-to-render relay; adds effect-processing cost, with actual latency dependent on the APO and graph. | Requires a COM APO, audio-driver-style package/INF association, elevated installation, Windows-version-specific packaging, real-time-safe code, signing and hardware/HLK validation obligations. OEM endpoint packages and Windows updates affect integration. | Better eventual native integration, but too much deployment and signing surface for the current repository. WDK/HLK/signing tools are not present here. |
| Custom virtual audio driver (Microsoft SysVAD starting point) | Most control over endpoint behavior and buffering, but requires WDM/WaveRT driver work plus user-mode engine. | Requires Visual Studio + Windows SDK + WDK, driver package installation, elevation, testing on a target machine, and a trusted signed package. Test-signing changes boot/security state; public release requires release signing/certification. | Not implemented. A test-signed custom driver is not an appropriate silent install on the user's daily PC. |
| WASAPI loopback on a physical speaker endpoint | No extra endpoint dependency, but the original endpoint continues to play its unprocessed signal; forwarding it elsewhere causes duplicate playback. | Useful for analysis and explicit relay testing only. | Not a solution for replacing system output. |

Microsoft's APO guidance describes APOs as in-process COM objects with a real-time interface that must be nonblocking and packaged with driver/INF integration. Windows 11 uses the `AudioProcessingObject` INF class for applicable packages, and Windows 11 CAPX APIs have additional requirements. Microsoft's SysVAD sample is a WDM virtual audio driver and requires the WDK and signed deployment. See [APO implementation](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/implementing-audio-processing-objects), [Windows 11 APO APIs](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/windows-11-apis-for-audio-processing-objects), [APO deployment](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/deploying-audio-processing-objects), [SysVAD](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/sample-audio-drivers), and [driver release signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/signing-a-driver-for-public-release).

The current host has the Windows SDK user-mode headers (`um`, `shared`, `winrt`, and `cppwinrt`) but no WDK build tree, kernel-mode headers, or kernel-mode libraries. Microsoft's SysVAD is a sample, not an install-ready audio cable; the documented sample can simulate capture/loopback with generated tone rather than mixing arbitrary app streams. An actual SonicSync virtual endpoint therefore needs substantial WaveRT/KS driver and user-mode-engine work, then test-host deployment and driver signing. The safest feasible interim route remains an explicitly installed, vendor-supplied virtual cable plus the already-built user-mode relay. No endpoint driver was installed or changed in this milestone.

## Required virtual endpoint

No virtual audio endpoint is installed on the development host. An optional compatible endpoint is [VB-CABLE from VB-Audio](https://vb-audio.com/Cable/). Its vendor describes it as a Windows virtual audio driver, states support for Windows 11, and lists its license as donationware; personal users should review the current vendor terms. SonicSync does not redistribute this driver. See the [vendor reference manual](https://vb-audio.com/Cable/VBCABLE_ReferenceManual.pdf) for its supported formats, installation, latency configuration, and removal procedure.

To set up routed playback:

1. Obtain the endpoint driver from its vendor, extract it locally, run its x64 setup as Administrator, and reboot as the vendor instructs. SonicSync does not perform this installation.
2. In Windows **Settings → System → Sound**, select the virtual playback endpoint (VB-CABLE labels this **CABLE Input**) as the output for Windows or for each target app in Volume Mixer. This is an explicit routing change; SonicSync does not make it.
3. In SonicSync **Devices**, cycle **Source** to that same virtual render endpoint, and **Output** to the actual headphones/speakers. They must be different endpoints.
4. Click **Start external route**. Play audio in the apps routed to the virtual endpoint. SonicSync's Equalizer controls update the route while it runs. Bypass fades to the original captured PCM signal before rendering it onward.

The current bridge accepts mono or stereo source endpoint mix formats and initializes capture and render with the source mix format in shared mode. WASAPI may convert for the output endpoint; SonicSync does not negotiate multichannel layouts or measure whether those conversions add latency. Configure a virtual endpoint as stereo for this build. Bit-perfect output is not expected while DSP is enabled. Protected/exclusive-mode or app-specific routing may not pass through this path.

## Reproducible validation plan

1. Confirm the render endpoints in SonicSync **Devices**. With VB-CABLE installed, confirm its playback endpoint appears (normally **CABLE Input**). Keep a physical output selected separately.
2. Set a single test application’s Windows Volume Mixer output to the virtual endpoint. Leave other apps on their existing devices.
3. Start the SonicSync route. Confirm **Route ready · waiting for audio**, then play from the test app. The UI should show **External audio is processed** only after non-silent samples arrive; spectrum and meter values come from captured/post-DSP samples.
4. Use a known 100 Hz tone from the external test application. Record capture/output peaks in the route log or shared meter, then switch Neutral ↔ Hip-Hop without stopping playback. Confirm a repeatable low-frequency change and that the app keeps playing. Toggle bypass and verify the level returns to the captured input within the bypass transition.
5. Repeat with Spotify, YouTube Music, and a browser one at a time, recording app output selection, endpoint names, route state, and whether a signal was captured. These players have not yet been tested on this host. Do not infer audio routing from GSMTC title/artist metadata.
6. Test recovery by stopping SonicSync, restoring the app output in Windows Volume Mixer, and confirming direct playback resumes. Do not leave the system default pointing to the virtual cable after SonicSync exits.

Verified on this host: CTest's synthetic DSP response tests, local WAV playback, and a separate `sonicsync_player.exe` process feeding a 100 Hz WAV into WASAPI loopback from the Realtek endpoint and out to the LG endpoint. The route reported captured peak 0.019989; Neutral output was 0.019989 and Hip-Hop output peaked at 0.0266779. This verifies the loopback/DSP/render implementation with a second process, not a third-party application or virtual endpoint. The system endpoint list had no virtual cable.
## Recovery and removal

If audio stops, use SonicSync **Stop external route**. Then restore Windows output (and any per-app Volume Mixer routes) to the original physical device and restart playback apps. SonicSync never changes that default automatically. If SonicSync is not running, Windows will not hear apps still routed only to the virtual cable. To remove a third-party cable, use its own x64 setup's remove option as described in the vendor manual and reboot; then restore Windows output if needed. SonicSync itself has no driver service to uninstall.

## Verification status

The WASAPI route is compiled and shares the tested DSP core. The development host enumerates only physical render endpoints (Realtek headphones, NVIDIA LG monitor audio, Realtek 7.1 speakers, and Realtek speakers); no virtual cable endpoint is present. A controlled 100 Hz WAV from a separate `sonicsync_player.exe` process was rendered to Realtek headphones while the bridge captured that endpoint and rendered to the LG endpoint. Neutral measured captured/processed peaks of 0.019989 / 0.019989; Hip-Hop measured 0.019989 / 0.0266779. This verifies real endpoint loopback samples processed by the shared DSP and sent to a second endpoint, but not a third-party application's audio or the virtual-endpoint path. The external-application acceptance test is blocked until a virtual endpoint is installed and a real external player is routed to it.

The relay now places its child HRESULT in the shared control block when an established route exits with an audio error; the UI displays that code instead of implying recovery. This is error reporting, not hot-unplug reconnection. Latency, audio-device hot-unplug recovery, multichannel processing, per-app automatic route management, live media metadata/artwork, external-app/virtual-endpoint routing, and APO/driver packaging remain unverified or unimplemented.
